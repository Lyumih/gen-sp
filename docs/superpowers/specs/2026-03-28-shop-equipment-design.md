# Дизайн: магазин, золото, инвентарь, типизированная экипировка, Memento-прокачка предметов за победу

**Дата:** 2026-03-28  
**Статус:** утверждено после ревью спеки (ожидает вашего просмотра файла и план реализации)  
**Связь:** `docs/superpowers/specs/2026-03-28-gen-game-design.md`, `src/game/campaign/runReducer.ts`, `src/game/types.ts`, Memento: `rollCardLevelUp`, `resolvePercentValue`

## 1. Цель

Добавить в кампанию **экономику (золото)**, **магазин покупки предметов**, **инвентарь и экипировку по типизированным слотам**, а также **рост уровня надетых предметов после победы в сценарии** по правилам Memento Mori (тот же закон броска, что у `rollCardLevelUp`). Предметы влияют на **и героя в бою, и расчёт урона карт** в первой версии.

## 2. Принятые решения (brainstorming)

| Тема | Решение |
|------|---------|
| Прогрессия vs магазин | **B:** основной рост силы предметов — с побед; магазин — покупка новых экземпляров. |
| Закон прокачки | **Memento:** после победы с шансом `+1` к уровню предмета; кривая как у карт (`rollCardLevelUp` / общая `rollMementoLevelUp`). |
| На кого бросок | **A:** отдельный бросок **на каждый надетый** предмет (по занятым слотам). |
| Валюта | **A:** **золото**; магазин принимает только его; начисление с побед. |
| Эффект предметов | **C:** **и** бонусы к **maxHp** героя, **и** вклад в **эффективный уровень** для `resolvePercentValue` при ударе картой. |
| Слоты | **A:** **фиксированные типы** слотов (например `weapon` / `armor` / `accessory`); в слот только предмет совместимого типа. |

## 3. Модель данных и состояние

### 3.1. Экземпляр и шаблон

- **`ItemInstance`:** `{ id: string; templateId: string; itemLevel: number }` — все экземпляры лежат в одном месте в кампании.
- **`ItemTemplate`** (контент, без React): `slot` (`EquipmentSlot`), `shopPrice` (золото), поля бонусов, например:
  - `hpBonusPerItemLevel` — вклад в **дополнительный maxHp** героя (сумма по надетым: `hpBonusPerItemLevel * itemLevel`);
  - `cardLevelBonusPerItemLevel` — вклад в **агрегат**, который **прибавляется** к `global_level` карты при расчёте урона через `computeCardAttackDamage` / `resolvePercentValue`.

Точные имена полей и каталог шаблонов — на этапе реализации; семантика: **линейно от уровня предмета**, без стеков и без дубликатов одного `id`.

### 3.2. Кампания

Расширить **`CampaignState`**:

- `gold: number`
- `items: ItemInstance[]`
- `equipment: Record<EquipmentSlot, string | null>` — значение: `id` предмета из `items` или `null`.

Инварианты:

- Каждый `id` в `equipment` существует в `items` и шаблон предмета имеет тот же `slot`, что ключ записи.
- Один предмет не может быть надет **дважды**; экипированный предмет остаётся в `items`.
- Если `itemId` уже указан в `equipment` в **другом** слоте, `EQUIP_ITEM` с этим `itemId` в другой слот → **no-op** (сначала `UNEQUIP_ITEM`).
- Если `equipment[slot] === itemId` уже выполнено, повторный `EQUIP_ITEM` с теми же аргументами → **no-op** (идемпотентно, состояние без изменений).

### 3.3. Снимок попытки боя

Расширить **`BattleAttemptSnapshot`** полями **`gold`**, **`items`**, **`equipment`** (копия структуры на момент входа в бой), чтобы **retry после поражения** откатывал экономику и экипировку так же, как карты и `worldPower`.

`BattleAttemptSnapshot` при старте боя собирается из актуального `CampaignState` (аналог `snapshotFromCampaign`).

## 4. Действия рана (`RunAction`)

| Действие | Назначение |
|----------|------------|
| `BUY_ITEM` `{ templateId }` | Достаточно `gold` → списание цены из шаблона, создание нового `ItemInstance` (новый `id`, стартовый `itemLevel`, согласовать с дизайном, напр. `1`), добавление в `items`, **без** автоматической экипировки. |
| `EQUIP_ITEM` `{ itemId, slot }` | Предмет есть в `items`, шаблон совпадает с `slot`, предмет **нигде** не экипирован (см. §3.2). Если слот **занят**: предыдущий предмет остаётся в `items`, слот получает новый — **одна атомарная замена** (без обязательного `UNEQUIP`). **No-op** только при невалидном действии (нет предмета, неверный тип слота, предмет уже в другом слоте и т.д.), а не из-за того, что слот был занят. |
| `UNEQUIP_ITEM` `{ slot }` | `equipment[slot] = null`, предмет остаётся в `items`. |

Недопустимые комбинации → **no-op** (состояние не меняется); при необходимости UI показывает причину через `App.useApp()`.

## 5. Победа, золото, броски Memento

### 5.1. Золото

При успешном **`FINALIZE_VICTORY`** начислять золото по правилам из одного модуля (например «награда за сценарий»): база за прохождение сценария и опционально надбавка за число/тип врагов. Конкретные числа — константы баланса, не размазаны по редьюсеру.

### 5.2. Уровни предметов

Порядок бросков задаётся **явным** массивом в коде, например `const EQUIPMENT_ROLL_ORDER: readonly EquipmentSlot[] = ['weapon', 'armor', 'accessory']`. Обходим слоты **в этом порядке**, пропускаем `null`; для каждого занятого слота:

1. Найти предмет по `id`.
2. Вызвать тот же бросок, что для карт: `rollCardLevelUp(item.itemLevel, roll)` или общая **`rollMementoLevelUp`**.
3. При успехе: `itemLevel += 1` в соответствующем элементе `items`.

`itemLevelRolls[i]` соответствует **i-му занятому** слоту в порядке `EQUIPMENT_ROLL_ORDER`.

### 5.3. RNG и тестируемость

Как для `USE_CARD_ATTACK`: **расширить** действие **`FINALIZE_VICTORY`** полем **`itemLevelRolls: number[]`** (каждое значение в диапазоне 1…100). В **том же** кейсе редьюсера, после проверки `phase === 'victory'`: начислить золото (модуль награды), применить броски к предметам, затем перенести в кампанию `worldPower`, `cards`, обновлённые **`items`**, **`gold`**. Отдельное действие «только награда» не вводить.

Ожидаемая длина: число **занятых** слотов в порядке `EQUIPMENT_ROLL_ORDER` на момент финала. Если **`itemLevelRolls.length`** не совпадает с этим числом → **`FINALIZE_VICTORY` целиком no-op** (фаза и кампания без изменений). Если ни один слот не занят — пустой массив.

UI генерирует значения; ядро остаётся детерминированным. Семантика **`battleAttemptId`** для защиты от двойных наград не меняется.

## 6. Влияние на бой

### 6.1. Герой

В **`makeHero`** (или отдельной чистой функции, вызываемой оттуда): после базового `computeUnitStat` по сценарию и `playerUnitLevel` / `worldPower` добавить **суммарный бонус maxHp** от надетых предметов (из шаблонов × `itemLevel`). Текущее правило «полное HP в начале боя» сохранить: `hp = maxHp`.

### 6.2. Карты

При вычислении урона карты использовать **эффективный уровень**:

`levelForDamage = card.global_level + aggregateCardLevelBonusFromEquipment(equipped items, templates)`

и передать его в **`computeCardAttackDamage`** (или расширить сигнатуру явным вторым слагаемым — на усмотрение реализации при сохранении одного места вызова). Правило **«уровень до прогресса карты на этот удар»** для `applyCardUse` не меняется; бонус экипировки — **контекст боя**, не увеличивает `global_level` карты.

## 7. UI (v1)

- **Хаб кампании:** блок или вкладка **«Магазин»** — список шаблонов (цена, слот), покупка → `BUY_ITEM`.
- **«Инвентарь / экипировка»:** неэкипированные предметы + слоты с выбором только подходящего типа; `EQUIP_ITEM` / `UNEQUIP_ITEM`.
- Экран **победы:** при нажатии «продолжить» — сгенерировать `itemLevelRolls` нужной длины и вызвать **`FINALIZE_VICTORY` с payload** `{ itemLevelRolls }` (единый переход в хаб с мержем меты и боя).

## 8. Сохранение и миграция

Расширить **`normalizeLoadedCampaign`** в `src/game/persistence/migrate.ts` (или эквивалент): при отсутствии полей подставить `gold: 0`, `items: []`, все ключи `equipment` → `null`. После загрузки: слоты `equipment`, указывающие на `id`, которого нет в `items`, **сбросить в `null`**. При несовместимом изменении схемы сохранения — инкремент **`SAVE_VERSION`** в `schema.ts` и ветка миграции (как принято в проекте).

Не полагаться на «доверчивый» cast без нормализации: старый JSON не должен оставлять `undefined` у новых полей.

## 9. Тестирование

| Уровень | Проверка |
|---------|----------|
| Чистые функции | Агрегаты бонусов от экипировки; `rollMementoLevelUp` при необходимости |
| `runReducer` | Покупка, экип/снятие, `FINALIZE_VICTORY` с фиксированными `itemLevelRolls` и золотом; уровни предметов и золото совпадают с ожиданием |
| `FINALIZE_VICTORY` | Неверная длина `itemLevelRolls` → no-op; победа без экипировки — `[]`, только золото и мерж карт/`worldPower` |
| `BUY_ITEM` | Ровно хватает золота / не хватает на 1 |
| `EQUIP_ITEM` | Занятый слот + валидная замена; уже в целевом слоте — no-op; уже в **другом** слоте тот же `itemId` → no-op |
| Снимок / retry | После поражения и retry мета (в т.ч. золото и предметы) совпадает со снимком попытки; нет двойного начисления награды за одну попытку |
| Снимок / экономика | В хабе купили предмет → вошли в бой → поражение → retry/abandon: `gold` и `items` как в снимке попытки |

## 10. Вне объёма v1 (YAGNI)

- Несколько валют, торговля между предметами, крафт.
- Уникальные легендарные эффекты с отдельными скриптами.
- Новые токены `%%` только от снаряжения (достаточно агрегата к уровню для урона).
- Прокачка предметов за убийство **внутри** боя (только **финал победы сценария** по этой спецификации).
