# Дизайн: читаемые характеристики предметов и умений, профиль героя, инспектор врага

**Дата:** 2026-03-28  
**Статус:** черновик после brainstorming (секции 1–3 согласованы); после вашего просмотра — план реализации  
**Связь:** `docs/superpowers/specs/2026-03-28-shop-equipment-design.md`, `docs/superpowers/specs/2026-03-28-gen-game-design.md`, `src/game/content/itemTemplates.ts`, `src/game/content/cardTemplates.ts`, `src/game/equipment/aggregates.ts`, `src/game/content/cardAttackDamage.ts`

## 1. Цель

- **Предметы** и **умения (карты)** отображают **понятные производные** от шаблонов и уровней (не только внутренние id и сырые поля).
- **Магазин** показывает те же смысловые характеристики, что и остальной UI (слот, эффекты за уровень предмета).
- **Профиль героя:** одна сводка **текущих** боевых/экономических характеристик и экипировки; **без** таблицы «статистика за всё время» между сессиями.
- **Доступ к профилю:** **и в хабе кампании, и в бою** (один и тот же смысл контента), без необходимости выходить с экрана боя.
- **Враги (фаза 2):** когда у врага в данных есть предметы/характеристики, игрок может **открыть инспектор** и прочитать их теми же принципами, что и свою экипировку.

## 2. Фазы

| Фаза | Содержание |
|------|------------|
| **1** | Описания предметов и карт, магазин, инвентарь/экипировка, список карт в бою, модальное окно профиля героя (хаб + бой). |
| **2** | Расширение контента/модели врага опциональной экипировкой; расчёт maxHp (и прочих производных) согласован с отображением; инспектор врага в бою. |

## 3. Архитектура и границы

### 3.1. Единый слой описаний (рекомендованный подход)

Ввести **чистые функции** без React (например под `src/game/uiCopy/` или рядом с `content/` — на этапе плана зафиксировать один модуль), которые принимают шаблоны/уровни/контекст и возвращают **структурированное описание** (строки для заголовка, списка бонусов, подсказок) или готовые фрагменты для UI.

- **Предметы:** из `ItemTemplate` и `itemLevel` выводить вклад в **maxHp** (`hpBonusPerItemLevel * itemLevel`) и вклад в **уровень для урона карт** (`cardLevelBonusPerItemLevel * itemLevel`); дублировать «за уровень предмета» текстом там, где показывают шаблон без экземпляра (магазин: ориентир **уровень 1**).
- **Карты:** цепочка **`CardInstance.templateId` → `getCardAttackTemplate` (`cardTemplates.ts`) → `CardAttackTemplate`**. Сейчас **`templateId` карты совпадает с ключом** в `CARD_ATTACK_TEMPLATES`; отдельное поле `attackTemplateId` не вводить без необходимости. По шаблону и **эффективному уровню для урона** (`card.global_level + gearCardLevelBonus` в бою, см. спеку экипировки) показывать вид атаки, `maxRange`, токен урона (`damageToken`) и **число** через `computeCardAttackDamage`, чтобы совпадало с боем.

Переиспользовать агрегаты `aggregateGearHpBonus` / `aggregateGearCardLevelBonus` из `src/game/equipment/aggregates.ts` для **суммарных** строк в профиле.

### 3.2. Имена для игрока

- У предметов уже есть **`label`** в `ItemTemplate`. У **`CardAttackTemplate`** поля имени пока нет; в UI отображается сырой `templateId`. Ввести **отображаемое имя** для карт: либо поле **`label`** (или эквивалент) в типе шаблона атаки в `cardTemplates.ts`, либо одна таблица **`templateId → label`** в одном модуле контента — одно место правды для списка карт и профиля.

### 3.3. UI-компоненты

- **Профиль героя:** общий компонент (например `HeroProfileModal`), открывается кнопкой с текстом и `aria-label` (например «Профиль героя») из `CampaignHub` и `BattleScreen`. Контейнер: **Modal** (v1), фокус и Esc по правилам Ant Design.
- **Магазин / инвентарь / Select:** короткие подписи в кнопках и опциях; полные детали — в профиле и/или **Popover** на опции или у выбранного слота (не раздувать `Select`).
- **Карты в бою:** компактная строка; детали — **Collapse** или **Popover** по клику (дальность, тип, токен, расчётный урон).

Ядро боя и редьюсеры **не** должны зависеть от React; только чтение состояния и вызов чистых функций из UI.

## 4. Содержимое профиля героя (фаза 1)

Минимальный набор:

- `playerUnitLevel`, `worldPower`, `gold`.
- Суммарные **бонусы экипировки:** доп. maxHp от шмоток, суммарный бонус к уровню для урона карт (как в бою на старте попытки — для согласованности с `gearCardLevelBonus` в `BattleState` при открытии из боя).
- Список **надетых** предметов по слотам с полными описаниями из слоя §3.1.
- Опционально краткий список карт (имя, уровень, использования) — без дублирования всего бойового UI; детали карты по раскрытию.

**Хаб vs бой:** в `CampaignState` нет живого юнита героя; **текущие HP/maxHp на поле** показывать **только в бою** (из `BattleState` / `Unit`). В хабе — мета (`playerUnitLevel`, `worldPower`, `gold`), экипировка, суммарные бонусы от шмоток; при необходимости одна строка **«ожидаемый maxHp в следующем бою»** по тем же правилам, что `makeHero` / сценарий (база + `worldPower` + агрегат HP от экипировки) — на этапе реализации зафиксировать одну чистую функцию, чтобы не расходилось с входом в бой.

**Вне объёма:** глобальная статистика между сохранениями, достижения, история забегов.

## 5. UX (зафиксировано в brainstorming)

- Магазин: название, цена, слот, эффекты «за уровень предмета»; для некупленного — пример на **уровне 1** + мелкая оговорка про рост после побед.
- Не перегружать списки: коротко везде, развёрнуто в модалке профиля и вспомогательных Popover.
- Доступность: смысл в тексте, иконки с `aria-hidden` где применимо.

## 6. Фаза 2: враги

### 6.1. Данные

- У записи врага в сценарии (или эквиваленте контента) — опциональный список экипировки. Допустимые формы: массив **`{ templateId, itemLevel }`** (достаточно для отображения и формул) или полноценные `ItemInstance` с локальными id, если удобнее стыковать с существующими функциями.
- При **отсутствии** списка поведение и расчёты как сейчас.

### 6.2. Согласованность

- **maxHp** (и другие производные, если появятся) врага считаются **с учётом** бонусов предметов теми же правилами, что у героя (`hpBonusPerItemLevel * itemLevel` и т.д.), чтобы цифры в инспекторе совпадали с `Unit` на поле.

### 6.3. UI

- Клик по **живому** врагу (или отдельная кнопка «Инфо» на ячейке) открывает **Modal**: id/метка, HP, уровень, список предметов с теми же описаниями; при отсутствии предметов — всё равно HP/уровень и при необходимости одна **человекочитаемая** строка про базовую выносливость сценария (без сырого имени поля в UI).

### 6.4. Инварианты

- Инспектор только **чтение**; не изменяет `BattleState`.
- Экипировка врага на момент входа в бой — **снимок**; изменение внутри боя в **фазе 2+** при необходимости явно хранить на юните или в состоянии боя (YAGNI до требования).

**Вне объёма на старте фазы 2:** отдельные «черты» вне предметов — только если не выразить шаблонами предметов.

## 7. Ошибки и краевые случаи

- Отсутствующий шаблон предмета: безопасный fallback (`templateId` + предупреждение в dev при необходимости).
- Карта без шаблона атаки: показывать известные поля `CardInstance`, урон не считать.
- `damageToken` не парсится: показать токен и `fallbackDamage` по правилам `computeCardAttackDamage`.
