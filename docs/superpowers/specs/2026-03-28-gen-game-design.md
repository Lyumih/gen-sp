# Gen — дизайн игры и системы «Memento Mori»

**Дата:** 2026-03-28  
**Статус:** rev 1 — после внутреннего ревью (уточнены правила смерти, `%%`, канонический бросок уровня карты, MVP по модификациям и поражению)

## 1. Краткое описание

**Gen** — 2D RPG с бесконечной системой улучшений **«Memento Mori»**: сражения с врагами, оружие, умения и их улучшения; сила растёт с каждым боем. **Враги усиливаются при каждой смерти** (свой или чужой — см. §6).

**MVP боёв (согласовано ранее):** пошаговая тактика на **квадратной сетке**, **4 ортогональных направления**; **цепочка из нескольких боёв** без карты мира; ближний и **дальний** бой с ограничением дальности; HP; **автосохранение** в `localStorage` с версионированием схемы.

**Архитектура реализации (утверждено):** ядро игры отдельно от React (**чистые функции** + типы), UI на Ant Design, состояние через **Zustand**, персистентность — адаптер `localStorage`.

---

## 2. Система «Memento Mori» — источники прокачки

Прокачка с **шансом** и в **разных контекстах**:

| Условие | Что прокачивается |
|---------|-------------------|
| **Смерть** | Уровни **врагов** и **персонажей** (игрока) — по правилам шанса для сущности. |
| **Использование** | **Умения** и **оружие** (карточки/навыки с глобальным уровнем карты). |
| **Победа** | **Модификации** умений и оружия (отдельные уровни модификаций). |

Идея **ортогональности** сохраняется: смерть качает сущности / мета-силу мира; использование — активные карты (скиллы/оружие); победа — слой модификаций, не дублирующий прокачку «за использование».

**MVP (зафиксировано):** начисление к модификациям — **за каждого побеждённого врага** (каждое убийство в бою может дать бросок/очки на выбранные открытые модификации по правилам контента), а не один раз за весь бой. При необходимости упростить до «за бой» — только осознанное изменение спеки.

## 3. Нотация `%%` для числовых параметров умений

**Источник уровня для токена:** по умолчанию **глобальный уровень карточки** (§4), для которой описано умение/оружие; если в контенте указано иное — явная пометка в данных карточки.

**Взаимоисключение форм:** в одном токене используется **ровно одна** форма: либо `BASE%%`, либо `BASE%%CAP` (CAP > 0), либо `BASE%%-P` (P > 0). Не комбинировать суффиксы в одном литерале.

**Грамматика (для парсера):** целое `BASE`, затем `%%`, затем опционально целое `CAP` или `-` и целое `P`. Рекомендуемый шаблон: `-?\d+%%(-?\d+)?` с валидацией веток.

### 3.1. Базовая форма `BASE%%`

- Множитель от уровня карточки `L`: `value(L) = BASE × (1 + 0.01 × L)` (без верхней границы по уровню; бесконечный рост числа — см. баланс и UI).
- Пример: «**40%%** урона» — при `L=0` → 40; при `L=100` → 80.

### 3.2. Ограничение роста на отрезке 100 уровней: `BASE%%CAP` (CAP > 0)

- На уровнях `L = 0…100` множитель к базе растёт **от 1 до `(1 + CAP/100)`** (линейно по `L`: `value(L) = BASE × (1 + (CAP/100) × (L/100))` при `L≤100`; при `L>100` — продолжение по отдельному правилу баланса или заморозка на множителе у `L=100` — **зафиксировать в коде одним вариантом**).
- Пример: **`40%%50`** при `L=100` → `40 × 1.5 = 60`.

### 3.3. Форма `BASE%%-P` (P > 0) — референс из требований

**DECIDED для реализации v0:** трактовать как **множитель к базе** `(1 - P/200)` в **референсной точке** `L_ref = 100` при сравнении с линейным ростом `BASE%%`, подобранной так, чтобы выполнялся пример автора: **`40%%-50` → 30** ⇔ `40 × (1 - 50/200) = 40 × 0.75 = 30`. Для других `L` применять ту же норму относительно выбранной кривой (документировать в коде рядом с `resolvePercentToken`).

### 3.4. Парсинг

- В контенте — строки с одним токеном `%%` на числовой плейсхолдер; движок подставляет число через **`resolvePercentToken(base, L, mode)`**.
- Обязательные unit-тесты: `40%%` при L=0,100; `40%%50` при L=100; `40%%-50` при L_ref; конфликтующие строки с двумя `%%` в одном числе — запрещены валидатором контента.

## 4. Уровень карточки (умение / оружие) и шанс улучшения при использовании

### 4.1. Поведение

- Каждая **карточка** (умение или оружие) имеет **глобальный уровень** со **стартом 1** (не 0), чтобы «на уровне 1 шанс 100%» совпадал с §4.2–4.3; растёт **на 1** при успешном срабатывании шанса.
- При **каждом использовании**:
  1. Увеличить счётчик использований.
  2. Бросок `1…100` (равномерно).
  3. Успех улучшения уровня карточки — по правилу ниже.

### 4.2. Кривая шанса

- На **уровне карточки 1** (перед первым апом: стартовый уровень считаем **1** для кривой; счётчик успешных апов согласовать с данными сохранения) шанс **100%**.
- К **уровню 100** шанс падает до **1%**.
- **После 100** — фиксированные **1%**.

**DECIDED — линейная интерполяция порога между 1 и 100:** пусть `L` — текущий глобальный уровень карточки. Для броска `r` ∈ `1…100` равномерно:

- если `L > 100` — успех тогда и только когда `r === 1` (ровно **1%**);
- если `1 ≤ L ≤ 100` — успех тогда и только когда `r === 100` **или** `r ≥ L`  
  (при `L=1` все `r` дают успех; при `L=100` только `r=100`).

### 4.3. Каноническая функция (нормативная)

```ts
/** Возвращает true, если карточка повышает global_level на +1 после использования. */
function rollCardLevelUp(currentLevel: number, randomInt1to100: number): boolean {
  const r = randomInt1to100
  if (currentLevel > 100) return r === 1
  return r === 100 || r >= currentLevel
}
```

Вызов из игры: инжектировать RNG (тесты подставляют детерминированные `r`). Примеры на JS/Godot из обсуждения с авторами — **нормативно не использовать**; только эта функция.

### 4.4. Приложение A (исторический референс, не для портирования дословно)

```js
// Опечатка his → this; логика может расходиться с §4.3 после L>100
chance_global_level_up() {
  this.uses_count(this.uses_count() + 1)
  const random = Math.floor(Math.random() * 100 + 1)
  if (random >= 100 || random >= this.global_level()) {
    this.global_level(this.global_level() + 1)
  }
  return random
}
```

## 5. Модификации (каждые 75 уровней карточки)

- **Открытие слотов:** первая модификация доступна при **глобальном уровне карточки ≥ 75**, вторая при **≥ 150**, и т.д. Число **разблокированных** модификаций: `floor(cardLevel / 75)` (при `cardLevel < 75` слотов **0**).
- У модификации **свой уровень**, растущий **отдельно** от уровня карточки.
- Прокачка модификаций: **только за победы над врагами** (см. §2 MVP); **не** за использование карточки.

## 6. Смерть и усиление врагов

**MVP (зафиксировано, одна ветка без форка):**

1. **Союзник (персонаж игрока в цепочке)** при **смерти в бою**: один бросок по таблице «рост уровня сущности» для **этого** персонажа (сохраняется в ране, если правила кампании позволяют воскрешение/продолжение; если ран заканчивается — уровень всё равно может быть записан для мета-прогресса — см. §7a).
2. **Враг** при **смерти**: мёртвый юнит не хранит долгосрочный уровень; вместо этого в **счётчик силы мира** `worldPower` (или аналог в сохранении кампании) добавляется приращение по шансу/формуле **отдельно от** карточек игрока. Следующие бои в цепочке используют `worldPower` при расчёте базовых статов врагов (см. §7).

Так фраза «враги сильнее с каждой смертью» означает **рост `worldPower` на смертях врагов**, а не уровень конкретного трупа. Смерть союзника **не** обязана в MVP увеличивать `worldPower` (опционально — фаза 2).

## 7. Согласование с тактическим MVP

- Бой остаётся **пошаговым на сетке**; карточки умений и оружие привязываются к **действиям** в бою (использование → §4).
- **Связь уровня сущности с боем (MVP):** базовые **HP, урон, защита** юнита на поле выводятся из **`unitLevel`** и **`worldPower`** формулой вида `stat = round(baseStat × (1 + α·unitLevel + β·worldPower))` с коэффициентами в данных баланса (точные `α, β` — в таблице баланса, не в спеке геймдизайна).
- Между боями: экран цепочки, применение наград победы к модификациям (§5), автосейв.
- **Поражение в бою (цепочка):** **MVP** — экран «поражение», **сохранение рана не стирается**; игрок **повторяет текущий бой** или **откатывается к началу цепочки** — выбрать одно поведение в UI и зафиксировать в плане реализации (рекомендация: **повтор текущего боя** с тем же сохранённым мета-прогрессом, без дюпа наград за победу).
- **Zustand** хранит UI-состояние и ссылку на **сериализуемый снимок** ядра; **миграции** сохранений обязательны при изменении схем.

### 7.1 Повторное прохождение сценариев (после финала цепочки)

Когда линейная кампания пройдена (`scenarioIndex` указывает «после последнего» сценария), игрок должен иметь возможность снова запускать бои по **любому** сценарию из `SCENARIOS` в том же сохранении; награды и мета ведут себя как в обычном бою, но **индекс прогресса цепочки не растёт**. Для корректного **retry** после поражения в снимок попытки нужно сохранять **индекс выбранного сценария**, а не полагаться на `scenarioIndex` кампании (после финала он вне диапазона массива сценариев).

Нормативно: [campaign-scenario-replay-design](./2026-03-28-campaign-scenario-replay-design.md).
