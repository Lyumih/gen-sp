# Gen — дизайн игры и системы «Memento Mori»

**Дата:** 2026-03-28  
**Статус:** черновик спецификации (brainstorming → review → план реализации)

## 1. Краткое описание

**Gen** — 2D RPG с бесконечной системой улучшений **«Memento Mori»**: сражения с врагами, оружие, умения и их улучшения; сила растёт с каждым боем. **Враги усиливаются при каждой смерти** (свой или чужой — см. §6).

**MVP боёв (согласовано ранее):** пошаговая тактика на **квадратной сетке**, **4 ортогональных направления**; **цепочка из нескольких боёв** без карты мира; ближний и **дальний** бой с ограничением дальности; HP; **автосохранение** в `localStorage` с версионированием схемы.

**Архитектура реализации (утверждено):** ядро игры отдельно от React (**чистые функции** + типы), UI на Ant Design, состояние через **Zustand**, персистентность — адаптер `localStorage`.

## 2. Система «Memento Mori» — источники прокачки

Прокачка с **шансом** и в **разных контекстах**:

| Условие | Что прокачивается |
|---------|-------------------|
| **Смерть** | Уровни **врагов** и **персонажей** (игрока) — по правилам шанса для сущности. |
| **Использование** | **Умения** и **оружие** (карточки/навыки с глобальным уровнем карты). |
| **Победа** (над врагом / итог боя — уточняется в §5) | **Модификации** умений и оружия (отдельные уровни модификаций). |

Идея **ортогональности** сохраняется: смерть качает сущности; использование — активные карты (скиллы/оружие); победа — слой модификаций, не дублирующий прокачку «за использование».

## 3. Нотация `%%` для числовых параметров умений

Плейсхолдер **`число%%`** задаёт **базовое значение** и **масштаб от уровня** карточки (или другого указанного уровня в контексте описания).

### 3.1. Базовая форма `BASE%%`

- Семантика (для спеки): за каждый уровень карточки эффективное значение растёт на **1% от базы** (аддитивно к множителю: `BASE × (1 + 0.01 × L)` при линейной модели по уровню `L`, если не задано иное).
- Пример текста: «Ваш меч наносит **40%%** урона за удар» — база 40 ед., дальше растёт с уровнем карточки по правилу выше.

### 3.2. Ограничение суммарного роста за 100 уровней: `BASE%%CAP`

- Второе число после `%%` — **целевой суммарный процент прироста от базы за диапазон 100 уровней** (не обязательно линейно по уровню; в реализации — кривая от 0 до `CAP%` за интервал 0…100 уровней).
- Пример: **`40%%50`** → за 100 уровней суммарный прирост **+50%** к базе → итоговый множитель **×1.5** на отметке «100 уровней карты» → **60** при базе 40.

### 3.3. Отрицательная модификация масштаба: `BASE%%-P`

- Минус перед числом — **сжатие или обратный тренд** масштабирования (точная формула — **обязательна к фиксации в реализации** до баланса).
- Пример из требований: **`40%%-50` → 30** в эталонной точке (интерпретация: например коэффициент **0.75** к базе в референсном состоянии, или иная формула; в коде — одна функция `resolvePercentToken(base, level, capOrSigned)` без двусмысленности).

### 3.4. Парсинг

- В контенте умений хранить строки с `%%`; движок на этапе расчёта заменяет токены на числа.
- Рекомендация: unit-тесты на `40%%`, `40%%50`, `40%%-50` и границы уровней.

## 4. Уровень карточки (умение / оружие) и шанс улучшения при использовании

### 4.1. Поведение

- Каждая **карточка** (умение или оружие) имеет **глобальный уровень**, растущий **на 1** при успешном срабатывании шанса.
- При **каждом использовании**:
  1. Увеличить счётчик использований.
  2. Бросок `1…100` (равномерно).
  3. Успех улучшения уровня карточки — по правилу ниже.

### 4.2. Кривая шанса

- На **уровне 1** шанс **100%**.
- К **уровню 100** шанс падает до **1%** (монотонно; конкретная кривая — линейная по уровню или по таблице — решается в реализации, график должен проходить через (1, 100%) и (100, 1%)).
- **После 100 уровня** шанс улучшения **фиксирован на 1%** (как у стабильного «докрута» в бесконечной прогрессии).

### 4.3. Эквивалентные формулировки (референс из обсуждения)

**JavaScript (исправлена опечатка `his` → `this`):**

```js
chance_global_level_up() {
  this.uses_count(this.uses_count() + 1)
  const random = Math.floor(Math.random() * 100 + 1) // 1..100
  const level = this.global_level()
  const cappedLevel = Math.min(level, 100) // для кривой 1→100; после 100 см. ниже
  if (random === 100 || random >= cappedLevel) {
    this.global_level(level + 1)
  }
  return random
}
```

Примечание: после `level > 100` условие должно давать **1%** успеха; в коде выносится в явную функцию `rollCardLevelUp(level) → boolean`, чтобы не дублировать расхождения.

**Godot (логика):**

```gdscript
var chance = randi_range(1, 100)
var success = (chance > level) or (chance == 1)
```

На уровнях 1 и 100 поведение согласуется с целевыми **100%** и **1%** при корректном диапазоне `level` и уточнении для `level > 100` (только `chance == 1`).

Итог: **одна каноническая функция** в ядре Gen (`rollCardLevelUp`), тесты против таблицы для уровней 1, 50, 100, 101.

## 5. Модификации (каждые 75 уровней карточки)

- За каждые **75 уровней** глобального уровня карточки открывается **слот/ветка модификации** (номер модификации `floor(cardLevel / 75)` или смещение — зафиксировать при контенте).
- У модификации **свой уровень**, растущий **отдельно** от уровня карточки.
- Прокачка модификаций: **только за победы** (например за победу над врагом или за завершение боя победой — выбрать одно правило и придерживаться везде).
- **Не** прокачиваются за использование карточки (отличие от §4).

## 6. Смерть и усиление врагов

- При **смерти** персонажа или врага срабатывает **шансовая** прокачка уровня **этой сущности** (отдельная таблица/формула для игрока и для врага).
- **«Враги становятся сильнее с каждой смертью»** трактовать как: при смерти врага (или при смерти союзника — если задумано глобально) враги получают прогресс — **уточнить в балансе**: только убитый враг, вся волна, или мета-уровень зоны. В MVP зафиксировать минимальный вариант (например: убитый враг имеет шанс повысить «уровень угрозы» следующих волн или конкретных спавнов).

## 7. Согласование с тактическим MVP

- Бой остаётся **пошаговым на сетке**; карточки умений и оружие привязываются к **действиям** в бою (использование → §4).
- Между боями: экран цепочки, применение наград победы к модификациям (§5), автосейв.
- **Zustand** хранит UI-состояние и ссылку на **сериализуемый снимок** ядра; **миграции** сохранений обязательны при изменении схем.
